# 测试方法

## 四个容易混淆的量

- **预填充 tok/s**：服务端报告本轮新输入的处理速度；冷输入要求 `cache_n=0`。
- **首字时间 TTFT**：客户端发出请求到收到第一段非空 `content`，使用单调计时器；包括 HTTP、排队、预填充和首段生成。不是仅用输入长度除以吞吐量。
- **生成 tok/s**：服务端 `predicted_per_second`，记录实际输出 tokens。达到上限的答案可能不完整。
- **请求完成时间**：客户端到完整响应结束的耗时。输出长度不同，不能把总时长差完全归因于推理配置。

本文 K = 1024 tokens，96K = 98,304，112K 上下文容量 = 114,688。tokens 不是汉字数，跨模型 tokenizer 的 tok/s 不直接可比。容量需容纳输入、输出和模板。

## 冷输入与缓存

`bench_prefill.py` 构造固定种子的合成记录，通过当前服务的 `/apply-template` 和 `/tokenize` 构造精确长度，关闭 prompt cache，断言实际输入数与缓存数，流式测量 TTFT。先做 4096 token 热身；热身不计入均值。首次编译/JIT 可能很慢，必须单独报告。

`bench_chat.py` 构造包含 10%、50%、90% 三处隐藏条目的 96K 输入，再用标准聊天模板添加固定的已知 assistant 答案和 follow-up，测缓存检索、代码、英文说明。固定 assistant 参考答案让两组后续输入完全一致；并非逐字复用每组实际生成答案。每轮保存 token 数组 SHA256。**同一模型做 MTP 对照时必须确认两组哈希完全相同**，并核对 batch、ubatch、KV 精度和运行库。

`bench_context.py` 保留最初历史检索方法：向已生成 assistant 前缀追加原生完成文本。它是 prefix-extension 微基准，不是规范聊天轮次；不能把其缓存数和聊天脚本混用。

`bench_short.py` 是代码与英文说明短输入对照。`bench_smoke.py` 检查简单算术、配置优先级和代码生成；默认只保存代码，`--execute-generated-code` 才执行 8 个功能样例。执行模式使用 AST 限制、独立 Python 进程和超时，**不构成安全沙箱**；可在一次性隔离环境中选择使用。

## 公平性与局限

历史数据大多每个场景一次；12K batch 扫描每项两次，无随机顺序、多轮置信区间、能耗或温度对照。因此报告的是观察值，不是稳定性能保证。首次代码生成曾出现约 43 秒 JIT，未当作稳态预填充使用。

历史官方基线与最终优化配置同时改变多个变量。它们适合比较完整使用体验；隔离 Q4 reorder 的比较须使用同一 FP16 构建的开关两组。MTP 公平长对照统一 batch/ubatch 2048，不能把它与 8192 的 no-MTP 配置直接当作 MTP 单变量实验。

检索检查只验证输出是否包含三个正确值，不是严格 JSON/schema 或长文理解评测。8 个代码测试和两个简单题只做冒烟检查，不能证明模型全面智能或全部答案正确。生成样本保留供人工复核。

本机在模型加载完成后做过一次 Windows working-set trim，随后未持续 trim；这会释放加载时遗留的可回收主存页。公开启动器通过可选 `--trim-working-set` 复现。显存/主存来自采样，可能漏掉瞬时峰值；进程 commit 不能当成物理 RAM 占用。

## 建议的新一轮流程

1. 记录硬件、驱动、OS、模型哈希、commit、编译器及完整参数；只运行一个槽和一个客户端。
2. 启动后热身，冷输入每长度至少 3 次；最好交替测试两配置并报告中位数与分布。
3. 同模型 A/B 比较 token 哈希；跨模型保留原始文档种子、字符数、token 数与任务准确性。
4. 核查 `cache_n`、实际输出数、MTP 接受率；保留完整响应，不只抄一个 tok/s。
5. 单独报告缓存续聊、首次加载/JIT、数值正确性及失败情况。

脚本输出到新的 `runs/` 子目录；已存在目录会拒绝覆盖。`--preset` 只是用户声明，metadata 同时标记其未由服务端完整核验，不能伪装成已确认的实际启动配置。
